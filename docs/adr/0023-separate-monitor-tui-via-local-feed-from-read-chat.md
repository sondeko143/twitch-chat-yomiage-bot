# 0023. read-chat にローカル配信口を設け、TUI は別プロセスの閲覧専用クライアントにする

- Status: Proposed
- 効力: 既定
- Date: 2026-10-03
- Related: [monitor TUI spec](../superpowers/specs/2026-10-03-tcyb-monitor-tui-design.md), [ADR-0020](0020-interval-option-on-show-chatters.md), [ADR-0021](0021-bound-401-retry-to-a-single-refresh.md), [ADR-0024](0024-websocket-json-for-monitor-feed.md)

## Context

配信中に視聴者・コメント・EventSub 通知を一望する TUI が欲しい。ところがコメントと通知は `read-chat` プロセスの IRC / EventSub ループ内でしか流れておらず、外から観測する経路が無い。

TUI はいつ閉じても、異常終了しても、読み上げを止めてはならない（利用者の要件）。

トークンは jfs ストア 1 ファイルに置かれ、401 を契機に遅延リフレッシュされる。同じストアを複数プロセスが同時にリフレッシュする設計にはなっていない。

## Decision

- `read-chat` の中に、コメント・通知・視聴者一覧・接続状態を流すイベントハブを置く。ハブは直近の分をリングバッファで保持する。
- `read-chat` は、ハブの内容をローカル IPC（`127.0.0.1` のみ）で配信する。既定は無効で、設定で有効にする。
- 新サブコマンド `tcyb monitor` を、その配信口に接続する閲覧専用の TUI にする。
- 読み上げ処理はハブへ送るだけにする。購読者の有無や遅さに読み上げは左右されず、取りこぼしは購読側の問題として扱う。
- 視聴者一覧の周期取得は `read-chat` の中で行う。間隔は配信口の設定と同じ場所に置く。
- `read-chat` 内の取得失敗は、401 リフレッシュ後の再失敗も含めて、接続状態として配信して次の周期で再試行する。`read-chat` は終了しない。
- `show-chatters` 単体の常駐は従来どおり ADR-0021 に従う。

## Alternatives rejected

- **TUI を read-chat に同居させる（`read-chat --tui`）** — TUI を閉じると読み上げも止まり、要件を満たさない。stderr ログと画面描画が衝突する問題もある。
- **TUI を独立プロセスにし、自前で IRC / EventSub / Helix に接続する** — 同じ jfs ストアのトークンを 2 プロセスがリフレッシュして競合する。接続処理と再接続処理が二重実装になる。同一アカウントで EventSub セッションと購読が重複する。さらに、読み上げられた内容と表示される内容が一致する保証も失う。
- **TUI 用に履歴を永続化する（SQLite 等）** — 必要なのは配信中のリアルタイム監視で、過去分は `read-chat` の起動中の分で足りる。永続化はスキーマと保存期間の管理を抱え込むだけで、今は得るものが無い。
- **視聴者一覧の間隔を CLI 引数にする（ADR-0020 の流儀）** — `read-chat` は常駐が本務で、間隔は実行ごとに変える値ではない。そのため設定に置く。ADR-0020 は自身の効力が他のサブコマンドへ及ばないと明記しており、この決定はそれと衝突しない。

## Consequences

- `read-chat` は IRC / EventSub ループの処理結果をハブへ送る形に変わる。これは将来 GUI などの購読者を足すときの土台にもなる。
- IPC は閲覧専用でローカル限定なので、認証を持たない。LAN 公開や操作系の RPC を足すときは、この前提を見直す新 ADR が要る。
- 保持件数を超えた古い履歴と、`read-chat` 再起動前の履歴は失われる。
