# 0019. show-chatters の常駐は前面ループに限定し、バックグラウンド化と再起動を OS に委ねる

- Status: Accepted
- Date: 2026-08-09
- Related: [show-chatters 常駐 spec](../superpowers/specs/2026-08-09-tcyb-show-chatters-daemon-design.md), [ADR-0020](0020-interval-option-on-show-chatters.md)

## Context

`show-chatters` を N 秒ごとにサンプリングし続けたい、という要求が出た。「daemon 化」には幅があり、前面常駐ループ・プロセスの自己デタッチ・Windows サービス登録のいずれもが該当しうる。

tcyb は配信者本人が配信中に手元で動かす単一利用者の bot で、既に `read-chat` が「窓を 1 つ占有し Ctrl+C で止める」前面常駐として運用されている。

常駐化すると、これまで「1 回叩いて終わる」で済んでいた失敗時の扱いを決める必要が出る。Twitch API には一過性のエラー（回線断・5xx・レート制限）があるが、恒久的な失敗（`moderator:read:chatters` スコープ不足による 403、チャンネル名の誤り）も同じ経路で返る。両者はレスポンスだけでは区別しにくい。

## Decision

常駐は**前面ループのみ**を実装する。プロセスのデタッチ・PID ファイル管理・Windows サービス登録は行わず、バックグラウンド実行と自動起動は OS 側の仕組み（タスクスケジューラ等）に委ねる。

- Ctrl+C を受けたら停止した旨をログに残し、終了コード 0 で終了する。
- 401 は従来どおりトークンをリフレッシュし、同じサンプルの取得を再試行する。
- 401 以外のエラーは握りつぶさず、その場でプロセスを非 0 で終了させる。再起動が要るなら外側の監督者が行う。
- 出力は stdout への 1 行 CSV のままとし、ファイルへの保存はシェルのリダイレクトに委ねる。

## Alternatives rejected

- **プロセスを自己デタッチしてバックグラウンド常駐する** — 停止のために PID ファイルとシグナル配送を自前で持つことになり、Windows ではさらにコンソール切り離しと job object の扱いが要る。手元で起動して配信終了時に止める運用では、`read-chat` と同じ前面常駐の方が「今動いているか」を見失いにくい。
- **Windows サービスとして登録する** — install / uninstall / start / stop のサブコマンドとサービス制御ハンドラが必要で、実装量が本題（N 秒ごとの取得）を大きく上回る。ログイン前から動かす要求も無い。
- **一過性エラーを握りつぶして次の tick へ進む** — 常駐は死ににくくなるが、スコープ不足やチャンネル名の誤りのような恒久的な失敗でもプロセスが生き続け、出力だけが止まる沈黙故障になる。落ちてくれた方が異常に気づける。
- **連続失敗 M 回で終了する** — 閾値 M に非自明な根拠が要るうえ、即終了との差は再起動までの遅延だけ。監督者を外に置く方針なら、いつ諦めるかの判断も外に出す方が単純。
- **`--output` でファイルへ追記する** — bot 側がファイルハンドル・追記・flush・ローテーションの責任を負う。1 行ずつ stdout へ出すなら、シェルのリダイレクトで同じ結果が得られる。

## Consequences

- 停止・自動起動・再起動ポリシーが利用者と OS 側の設定に露出する。README に運用例（リダイレクトでの追記、Ctrl+C での停止、落ちても自動復帰しないこと）を書く必要がある。
- 一過性の回線断でもプロセスが落ちるため、長時間の無人サンプリングでは外側の監督（タスクスケジューラの失敗時再実行など）が前提になる。
- Rust の stdout は行バッファリングされるため、`println!` 1 行ごとにリダイレクト先へ flush される。途中でプロセスが落ちても、それまでの行はファイルに残る。
- 将来「常駐自身が自己回復する」方針に転換する場合は、この ADR を supersede する。
