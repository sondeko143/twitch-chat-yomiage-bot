# 0018. プロファイル既定チェーンを operations 省略時のみ適用し単一 Command の複数 chains で送る

- Status: Proposed
- Date: 2026-07-26
- Related: [vstc_cli 既定チェーン spec](../superpowers/specs/2026-07-26-vstc-cli-default-chains-design.md), [ADR-0009](0009-add-process-routes-entrypoint-to-vstc.md), [ADR-0015](0015-single-profiles-toml-in-os-user-config-dir.md), [ADR-0016](0016-explicit-flags-override-profile-and-set-merges.md), [ADR-0017](0017-extend-vstc-routes-entrypoint-with-operand-options.md)

## Context

`vstc_cli send` は 1 回の実行で 1 チェーンしか送れず、チェーンは毎回位置引数で全部書くしかない。同じ入力を複数系統へ分けて流す構成（文字起こし結果を無翻訳・英訳・露訳の 3 系統に分け、それぞれ別ホストの字幕へ送る）では、系統ごとに長いコマンドを打ち直すことになる。

proto の `Command.chains` は `repeated OperationChain` で複数チェーンを表現できるが、`vstc` は常に 1 本の chain に固定して組んでおり、この表現力に到達していない。

プロファイル（ADR-0015 / ADR-0016）は host / port / config_path のスカラ値しか持たない。ここに「配列の配列」を初めて持ち込む。ADR-0016 が定めた「明示フラグ > プロファイル > 既定」の後勝ちルールはフィールド単位のスカラ上書きを前提にしており、チェーンの集合にそのままの形では適用できない。

route 文字列は `Url::parse` へ直接渡しているため絶対 URL しか受けず、`o:` スキームが必須になっている。`o:` は宛先でも操作でもなく、パーサを通すためだけの接頭辞で、設定ファイルにチェーンを何本も並べると全要素に現れる。あわせて、proto の `TRANSCRIBE` は `vstc` の変換表に載っておらず、文字起こしを route 文字列から指定できない。

## Decision

3 つを一体の決定として定める。

**1. 既定チェーンは `send` の位置引数を省略したときだけ適用する。** 位置引数を渡した実行では、プロファイルにチェーンが保存されていても送らない。ADR-0016 の「明示した側が勝つ」感覚を、フィールド単位ではなくチェーン単位で保つ。位置引数も既定チェーンも無い実行はエラーにし、送信しない。

**2. 複数チェーンは単一 `Command` の複数 `chains` として 1 回で送る。** チェーンごとに RPC を分けない。`Operand` は 1 つを共有し、`trace_id` も 1 つになる。

**3. route 文字列はスキーム省略形を正規化して受け付け、単一 route のパーサを `vstc` の公開 API にする。** `//` 始まりには `o:` を、スキームを持たない文字列には `o:/` を前置してから `Url::parse` に渡す。既存の `o:` 付き文字列はそのまま通る。あわせて `transc` / `transcribe` を `TRANSCRIBE` に対応づける。パーサを公開するのは、保存の時点で検証し、壊れた route を設定ファイルに残さないため。

保存・削除・確認は `profile set` のフラグではなく `profile chains` 配下の専用サブコマンドが担い、設定ファイル上のキー名は proto の語彙に合わせて `chains` とする。

## Alternatives rejected

- **位置引数と既定チェーンを常に合成する** — 既定ルートを常時流したい用途には向くが、位置引数で 1 本だけ試したいときに既定チェーンが黙って同乗する。ADR-0016 が全設定値に敷いた「明示した側が勝つ」の一貫性が、チェーンだけ破れる。
- **チェーンごとに別 Command を送る** — サーバが 1 chain しか見ない実装でも確実に動く利点があるが、N 本のチェーンが別々の `trace_id` を持ち、同一入力の追跡が分断される。加えて途中の 1 本だけ失敗したときの部分成功を CLI 側で定義する必要が出る。proto が `repeated` で複数チェーンを表現している以上、そこに載せるのが素直。
- **profiles.toml を構造化テーブルで書く（operation / remote / queries を別フィールド）** — `deny_unknown_fields` による typo 検出が効くのは operation と remote だけで、実際に打ち間違えやすい `queries` は proto 上 `map<string, string>` の自由キーなのでどちらの記法でも素通りする。得られる型安全は部分的な一方、`send` の位置引数（文字列）と設定ファイル（テーブル）で同じものの記法が二重化し、CLI で試した引数をそのまま保存できなくなる。typo の検出時期は記法とは独立で、文字列形式でも保存時に検証すれば同じ時点で落とせる。
- **設定ファイルでも `o:` を必須にする** — パーサに一切手を入れずに済むが、宛先でも操作でもない接頭辞がチェーンの全要素に並ぶ。`vstc_gui` が `remote` を `//host:port` 形式で持っている（ADR-0011 の FORWARD 置換も同じ形式）ことからも、`//host:port/op` は既にこのプロジェクトの語彙になっている。
- **`profile set --chain` を繰り返す保存方法** — 追加は 1 コマンドで書けるが、削除には別フラグ（全消去）が要り、途中の 1 本だけ消す操作を表現できない。`profile set` の「渡したフィールドだけマージ更新」（ADR-0016）はスカラ前提のモデルで、集合への追加・削除をそこへ載せると意味が二重になる。
- **位置引数も既定チェーンも無いとき、従来どおり空チェーンを送る** — 現行挙動の維持で後方互換だが、`--profile` の打ち間違いが無言の no-op として成功終了する。既定チェーンを導入すると「操作を書かない実行」が常用形になるため、この失敗様式の頻度が上がる。
- **パーサを公開せず送信時だけ検証する** — `vstc` の公開 API を増やさずに済むが、解釈できない route が設定ファイルに保存され、次回の送信まで発覚しない。保存を壊れた状態で成功させないほうが、設定ファイルの手編集を支援対象とする ADR-0015 の方針と揃う。

## Consequences

同じ入力を複数系統へ流す構成が、プロファイル名 1 つと `send -t <TEXT>` だけで実行できるようになる。N 本のチェーンが同一 `trace_id` を共有するので、サーバ側のテレメトリでも 1 回の入力として追える。

route 記法の正規化は受け付ける入力の拡張なので、既存の `o:` 付き設定・スクリプトは無変更で通る。同時に `send` の位置引数と tcyb が設定から読む操作文字列にも省略形が通るようになるが、これらの既存記述を書き換える計画は持たない。

`Profile` が初めて非スカラのフィールドを持つ。`profile set` の「渡したフィールドだけ更新」モデルの外に置いたため、プロファイルの編集手段が `set` と `chains` の 2 系統になる。`profile list` はチェーンの本数のみを示し、中身は `profile chains show` の担当とする。

ADR-0017 は `vstc` の公開送信口が 3 つになったことを留保として残した。今回さらに複数チェーン用の送信口とパーサが加わり、口は増える方向に進む。将来 `process_command` を含めて整理する余地は残るが、今回のスコープでは行わない。

proto の `SET_FILTERS` と `PING` は引き続き route 文字列から指定できない。今回は用途が無いため変換表に足さず、`TRANSCRIBE` のみ対応づける。
