# 0027. 配信チャンネル ID はトークンストアにキャッシュし、配信メッセージの状態は版を上げず任意フィールドで拡張する

- Status: Accepted
- 効力: 既定
- Date: 2026-10-03
- Related: [ADR-0023](0023-separate-monitor-tui-via-local-feed-from-read-chat.md), [ADR-0024](0024-websocket-json-for-monitor-feed.md), [ADR-0026](0026-receive-sub-events-via-chat-notification.md)

## Context

`read-chat` は EventSub の購読条件に使う配信チャンネル ID を、起動のたびに Helix の Get Users で引いている。この呼び出しが一時的に失敗すると、`read-chat` は起動時に終了する。bot 自身の `user_id` は既に jfs のトークンストアにキャッシュしており、2 回目以降の起動では API を呼ばない。

monitor の接続状態表示は、IRC と EventSub を WebSocket の接続直後に `connected` にしている。そのため、IRC のログイン失敗や、EventSub の購読失敗（再認可忘れによる 403 など）が TUI からは見えない。購読の一部失敗を表すには、配信メッセージの `status` に情報を足す必要がある。プロトコル版（ADR-0024）を上げると、版の違う monitor は非互換表示になり、何も表示しなくなる。

## Decision

- 配信チャンネルの login と ID の組を、トークンストア（`DBStore`）に保存する。設定の `channel` が保存済みの login と一致すれば、その ID を使い、API は呼ばない。一致しなければ引き直して上書きする。既存のストアファイルに項目が無い場合は、未保存として扱う。
- キャッシュが無いときの解決では、一時的な失敗（通信エラー・5xx）を間隔を空けて数回まで再試行する。4xx とチャンネル未検出は再試行しない。
- IRC は、ログイン完了の応答を受けてから `connected` にする。EventSub は、`session_welcome` を受けて購読処理を終えてから `connected` にする。
- 購読に失敗した種別の一覧を、`status` の任意フィールドとして追加する。プロトコル版は 1 のまま据え置く。受信側は、欠けたフィールドを既定値（空）として読み、知らないフィールドは無視する。

## Alternatives rejected

- **毎回引き直し、失敗時に無期限で再試行する** — 起動のたびに API を 1 回余計に呼ぶ。Twitch 側の障害中は、読み上げがいつまでも始まらない。チャンネル ID は login が変わらない限り不変なので、キャッシュで足りる。
- **チャンネル ID を設定ファイルに書かせる** — 利用者が ID を調べる手間が増える。`channel` と食い違った値を書かれても検出できない。
- **購読失敗用に `ConnectionState` へ新しい値（例: 部分接続）を足す** — enum に値を足すと、古い monitor が `status` を解釈できなくなる。結局プロトコル版を上げることになる。任意フィールドなら新旧どちらの組み合わせでも動く。
- **プロトコル版を 2 に上げる** — `read-chat` と `monitor` を同時に更新しない限り、TUI が非互換表示で止まる。追加情報のためだけに払うコストとして大きすぎる。

## Consequences

- 2 回目以降の `read-chat` 起動は、チャンネル ID 解決のための API 呼び出しを行わない。
- チャンネルの login が変わった場合は、設定の `channel` を変えれば引き直される。ID は不変なので、古い login のキャッシュが誤った ID を返すことは無い。
- 配信メッセージに後から情報を足すときは、任意フィールドで足すのが既定になる。既存フィールドの意味を変えるとき、または必須の情報を足すときは、プロトコル版を上げる。
